## Implemented contracts

Both original ABIs execute real WebAssembly through Chicory's Java interpreter. Modern imports contain 93 linked functions: Std 6, Net 15, Html 39, Defaults 2, JavaScript 12, Canvas 15, Env 4. The supplied legacy implementation contains 82: Std 29, Net 15, Html 30, Json 1, Defaults 2, Aidoku 5. Unknown imports fail explicitly. Each source has a serialized VM, restart after traps, bounded execution, and a device heap based linear-memory ceiling (at most 256 MiB, normally one third of the Java heap).

Modern postcard encoding preserves optional values, float widths, page context, raw metadata, chapter fields, source home components and dynamic settings. Legacy content ratings and left/right reading directions are converted explicitly; legacy KVC reads retain the old enum values. Fractional chapter upload seconds become millisecond timestamps. Legacy missing-object/array descriptors, null elements, JSON object/array restriction and date error values match the original host.

Page processing uses source-provided request modifications and actual Canvas image transforms. Context-bearing pages receive unique internal tokens, so two pages sharing an image URL retain separate processing contexts. Sidecars persist descriptions, thumbnails and original page payloads; `get_page_description` is invoked for modern deferred descriptions. The supplied legacy `create_page` ABI has no context/description/thumbnail arguments or dynamic-description export. Original legacy text/base64/URL pages are supported and their available metadata is persisted.

HTML imports use jsoup; network imports support scoped cookies, configurable parallel requests and rate limits, response cursors, parallel send, and challenge detection. Source settings are encrypted, preserve source-created defaults keys and Float/Data types, and can be exported/restored by the complete backup manager. ZIP installation rejects path traversal, symlinks, excessive file counts and oversized packages. Package upgrades retain an old copy until key migration and source configuration commit; a journal uses the committed SQLite version to recover interrupted upgrades.

The shared source UI retains source queries, filters, results, listings and page cursors across navigation. Cached jobs run in the ViewModel scope, and version/configuration changes cancel the old job. Query submissions retain immutable query/filter/listing snapshots; subsequent pages use that submitted snapshot and a request generation discards superseded responses. A child state observer cancels requests immediately on source configuration changes even while the page is hidden. It renders all seven original home component kinds, search pagination, source listings, library-specific Komga homes, dynamic filters/settings, authentication, OAuth PKCE, and source mirrors. Browse supports pin/disable/reorder/remove/update-all, original language/content-rating keys, compatibility ranges, aliases, source lists, native server setup, demo servers and package import. Native server clients implement Komga/Kavita/Suwayomi search, chapter/page metadata, filters, ordering, login modes, mirror failover, Kavita cookie OIDC/API keys and refreshed bearer credentials. Credentials are scoped to configured origins and stripped on cross-origin redirects.

JavaScript uses real Android Chromium for synchronous evaluation, DOM, promises and async functions. Document-start scripts implement user scripts, CSS hiding and request metadata. Content rules support block, block-cookies, make-https, css-display-none and ignore-previous-rules, with domain/top-URL/load-type/resource-type predicates. Ordinary fetch, XHR (including multipart files and synchronous binary bodies), navigator.sendBeacon, form submission and requestSubmit capture bodies before native interception. Beacon retains the native synchronous boolean queue/quota result, captures UTF-8 and binary BodyInit payloads with their Content-Type and include credentials, and removes exactly its own record if Chromium rejects the queue. Capture errors are explicit exceptions, not a fabricated true result. Requests to the same method/URL serialize capture until interception to prevent body/context mismatches. Source-provided non-GET web view loads retain the original HTTP method, body, content type and custom headers.

## Actual platform differences

- Chromium replaces WebKit; JavaScript/browser engine details, Android font availability and Canvas font metrics can differ. Unsupported recent WebView capabilities produce a System WebView update message instead of silently sharing cookies or dropping rules.
- Android's cookie-info API returns cookies matching requested URLs; it has no API that enumerates every cookie path/domain in a profile. All visited source URLs are queried and domain/path/expiry flags are preserved.
- `WebResourceRequest` exposes URL/method/headers but no request body. Document-start bridges cover ordinary page fetch/XHR/sendBeacon/forms and native source loads. Requests produced exclusively inside service-worker/browser internals without these document calls cannot supply an intercepted body through this API; such filtered requests fail visibly instead of submitting an empty body.
- Android interception does not supply WebKit's native resource classification. Script-assigned DOM URL kinds and fetch/XHR are recorded; parser/kernel requests use destination headers and URL inference.
- External OAuth providers can impose their own embedded-browser restrictions. This is provider policy, not an unfinished source authentication implementation. No user accounts were signed into during verification.

## Android 8 provider upgrade path

Temporary browsers have separate UUID profiles. Close stops and destroys the document, then clears its cookies, DOM storage, geolocation permissions and HTTP cache. Profile deletion retries at most four times without crashing the UI thread. Chrome 124 retains a loaded native profile until process exit, so this case is reclaimed at the next supported browser initialization: prefixed abandoned profiles are deleted before getProfile/setProfile can load them again. This follows the public ProfileStore contract; repeated delays cannot unload a provider-owned native context. Source browser isolation checks WebViewFeature.MULTI_PROFILE at runtime. It is a provider capability, not an intrinsic Android API-26 prohibition. AndroidX also requires a provider with multi-process support and that mode be enabled. On an eligible device, the official route is updating the allowed System WebView/Chrome provider through Google Play and selecting it in Android developer options. Android O and later require the provider to be installed and enabled for every device user profile. OEM allowlists/device policy can prevent a switch. These are compatibility conditions. The complete SDK35 browser suite has been tested; a compatible modern API26 provider remains absent from the current image.

Chrome 138 is the final release supporting Android 8/9; Chrome 139 requires Android 10. An Android 8 device needs its last compatible official provider rather than newest Chrome. The earlier stock API-26 image had no eligible WebView provider candidate in dumpsys; this prevented even ordinary WebView use and does not establish an Android-26 API prohibition or a measured isolation-feature failure. The official Google APIs API-26 x86_64 image, revision 16, is now installed. A read-only dumpsys check independently confirms Chrome 69.0.3497.100 as its eligible selected provider; this supplies ordinary WebView but lacks the modern profile capability required by the six source browser methods. The later official prebuilt inspection found that the apparent minSdk-26 APK was only a small stub; the complete provider packages available in that input require API 29. They do not supply a usable modern API-26 provider. The current API26 environment therefore still lacks a compatible, complete modern provider accepted by the system signature/allowlist; the six browser methods cannot be validated in that environment, while native and WebAssembly-only device checks are recorded separately. A capable official provider would enable the source APIs; that environment has not been validated here. The app reports that capability error instead of mixing source cookies. Maintenance clears supported stores and safely handles unavailable profiles; it does not turn an unsupported provider into a shared browsing profile. No third-party provider APK was downloaded.
